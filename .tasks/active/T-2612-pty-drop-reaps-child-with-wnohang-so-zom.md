# T-2612: PTY Drop reaps child with WNOHANG so zombie is never collected

## Context

`Drop for PtySession` (crates/termlink-session/src/pty.rs ~456-466) does:
```
libc::kill(pid, libc::SIGKILL);
let mut status = 0;
libc::waitpid(pid, &mut status, libc::WNOHANG);
```
The comment says "Reap to avoid zombie processes," but `WNOHANG` returns
immediately — right after `SIGKILL` the kernel has almost never delivered the
signal and transitioned the child to a zombie yet, so `waitpid` returns 0 and
reaps nothing. Every dropped PTY session (normal churn on the charter verb-4
"control terminal sessions" path) leaks a zombie until the host process exits.
DELICATE: a naive blocking `waitpid(pid, .., 0)` fixes the common case but must
consider (a) the child being a process-group leader with its own children —
SIGKILL to the leader does not kill the group; consider `kill(-pgid, SIGKILL)`;
(b) pid-recycle safety (only reap a pid we own); (c) Drop runs synchronously, so
a bounded/non-hanging reap is required.

## RCA

**Symptom:** Each dropped PTY session leaks a zombie child process; over a
long-lived hub with normal session churn the process table fills with `<defunct>`
entries.

**Root cause:** `waitpid(pid, .., WNOHANG)` immediately after `kill(SIGKILL)`
races the kernel — the child is not yet a zombie when `waitpid` polls, so it
returns 0 and collects nothing.

**Why structurally allowed:** The reap has a comment asserting it prevents zombies
(so it reads as intentional/correct), and no test asserts the child is actually
reaped after Drop — a false-confidence comment masked a no-op.

**Prevention:** A Drop-reaps-child regression test (spawn → drop → assert pid gone)
plus a bounded blocking reap. Consider generalizing to a small "reap this owned pid,
bounded" helper reused by other fork sites.
