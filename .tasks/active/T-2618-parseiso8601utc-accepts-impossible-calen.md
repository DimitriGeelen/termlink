# T-2618: parse_iso8601_utc accepts impossible calendar days (silent wrong-time)

## Context

`parse_iso8601_utc` (crates/termlink-cli/src/commands/remote.rs) range-checks month
(1–12), hour (≤23), minute (≤59), second (≤60) but validates day with a blanket
`1..=31` that is NOT month-aware. Impossible calendar days (`2026-02-30`,
`2026-04-31`, Feb 29 in a non-leap year) pass validation, then the epoch-days loop
silently rolls them into the following month — returning a wrong-but-plausible time
instead of `None`. T-2468 Reliability-#2 ("no silent failures") hunt.

- [x] Test proven load-bearing: temp-reverting the month-aware day check makes the new test FAIL

## RCA

**Symptom:** `parse_iso8601_utc("2026-02-30T00:00:00Z")` returns `Some(epoch-for-2026-03-02)`
instead of `None` — an impossible calendar date silently yields a wrong-but-plausible
timestamp. Same for `2026-04-31` (→ May 1) and Feb 29 in a non-leap year.

**Root cause:** The validation guard checked day with a month-independent `1..=31`
range, while every sibling field (month, hour, minute, second) got a correct bound.
The epoch-days computation then trusted the "validated" day and rolled the overflow
into the next month.

**Why structurally allowed:** The function is documented "deliberately permissive"
(input comes from our own writer), so the day-bound oversight looked intentional; the
existing test (`parse_iso8601_utc_rejects_malformed`) exercised month>12 and hour>25
but had NO day-of-month case, so the gap was untested.

**Prevention:** Month-aware day validation reusing the already-computed leap-aware
`mdays` table, plus a regression test covering impossible days (Feb 30, Apr 31, Feb 29
non-leap) AND valid boundary days (Feb 29 leap, Jan 31, Apr 30). Test proven
load-bearing via temp-revert.
