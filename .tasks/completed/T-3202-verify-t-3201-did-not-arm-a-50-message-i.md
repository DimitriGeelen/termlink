# T-3202: Verify T-3201 did not arm a 50-message injection backlog; prove the inbox rail end-to-end

## Context

Opened to check whether T-3201 (mirroring `inbox:` topics) armed a 50-message
injection backlog, and to prove the rail end-to-end rather than predict it.

## Findings

### 1. No backlog risk — two independent mechanisms bound it

`notify-injector.sh` does NOT scan the journal for work. It keys on the ARRIVAL
RECORD — `last_mail_ts` / `last_mail_topic` from the agent flag (`:151-161`) —
and exits "no new arrival ... already handled through $seen_ts" when that has
not advanced. Journal rows alone cannot trigger an injection.

Second, `:194-212` computes a `delivered` watermark as max(hub L3 watermark,
local `.delivered-offset` file). The code's own comment: a failed hub read "can
never re-open history that was already delivered". Even once triggered it cannot
replay below the watermark.

The 50 rows sit as history. **Verdict: safe.** Worth having checked — the S8
priority clamp exists precisely because a flood into a prompt is a denial of
attention, and I would have caused one by a different route.

### 2. I was WRONG about the next cron tick — the rail is still broken

I told the operator the rail "should now pick up AEF's consults on the next cron
tick". **It will not.** That was a prediction reported as a result.

`notify-sidecar.sh:229` — the component that WRITES `last_mail_ts` — enumerates
`--prefix "dm:"` only, exactly as `journal-mirror.sh` did. So after T-3201 the
journal ingests AEF's messages and the flag never advances for an `inbox:`
topic, so the injector never fires.

T-3201 was necessary and NOT sufficient. The rail is broken one layer further
along, for the identical reason.

### 3. Every dm-only enumeration, classified

Swept so the next gap is not found one layer at a time:

| site | role | verdict |
|---|---|---|
| `journal-mirror.sh:122` | journal ingest | FIXED (T-3201) |
| `notify-sidecar.sh:229` | writes the arrival flag | **BLOCKER — unfixed** |
| `journal-reaper.sh:117` | journal retention | inbox rows never reaped; unbounded growth, slow and non-urgent |
| `agent-reply.sh:132` | reply targeting | correct — replies target DMs |
| `agent-send.sh:339` | send-side scan | correct — outbound |
| `check-outbox.sh:181,185` | outbound audit | correct — documented scope is `dm:<self>:<peer>` |

### 4. Why the blocker is left unfixed

The change is a near-copy of T-3201's and would take minutes. Its FIXTURES would
not. `notify-sidecar.sh` decides that an agent has new mail and ultimately causes
text to be injected into a live prompt; shipping an untested change there to
finish inside one session is the wrong trade. Context stood at 70% against a 75%
stop line, so the honest choice was to record the finding rather than half-do the
fix.

**Next session:** fix `notify-sidecar.sh:229` with the same self-addressed filter
plus a fixture suite mirroring `tests/journal-mirror-inbox-fixtures.sh`. Then run
arc-011's own prover — `scripts/notify-rail-e2e.sh --stages
precond,deliver,receipt,ladder,wake` — against the `inbox:` path BEFORE telling
AEF anything has changed.

# The completion gate runs each command — if any exits non-zero, completion is blocked.
#
# Toolchain hint (L-291): if you edited *.vbproj/*.csproj/*.xaml add `dotnet build`;
# *.go → `go build ./...`; Cargo.toml → `cargo check`; tsconfig.json → `tsc --noEmit`;
# pom.xml → `mvn -q compile`. P-011 runs only what you write — broken builds slip
# past otherwise (origin: 003-NTB-ATC-Plugin T-077, broken WPF DLL on master 5 days).
#
# ── Pipefail/SIGPIPE: grepping a command's output (L-387, T-2090, T-2743, T-2738) ──
#
# THE DEFAULT — redirect to a file, then grep the file:
#     cmd > /tmp/.out 2>&1 && grep -q "PATTERN" /tmp/.out
#     curl -sf "$(bin/fw watchtower url)/page" -o /tmp/.out && grep -q "PAT" /tmp/.out
# Correct at any output size, and `&&` keeps the PRODUCING command's exit code in
# the verdict. Reach for this first; the alternative below is the special case.
#
# NEVER `cmd | grep -q PAT` (L-387) — why: P-011 runs each line under `set -eo
# pipefail`. When grep matches it exits and closes stdin while cmd is still
# writing, cmd takes SIGPIPE, the pipeline exits 141 — verification "fails" with
# the pattern present. Captured 4× (T-1716, T-1838, T-1862, T-1863).
#
# THE EXCEPTION — capture first, grep the capture:
#     out=$(cmd 2>&1); echo "$out" | grep -q "PATTERN"
# Valid ONLY while "$out" fits the 65536-byte pipe buffer, and it is on you to
# know that it does. Above that the form inverts and becomes the very failure
# L-387 describes: echo blocks on the full pipe, grep -q exits, echo takes
# SIGPIPE, rc=141 (T-2743 — measured on a 146,366-byte Watchtower page, 3/3 runs,
# deterministic not racy; rendered routes run 50-200KB, so anything that curls a
# page is over the line). It also discards cmd's exit code, so a 404 yields an
# empty capture that grep merely fails to match rather than a failed line.
# If you do use it: single pipe only, no intermediate tail/awk/sed stage between
# capture and grep (T-2090) — the middle stage is what `grep -q` slams its stdin
# on, and grep scans the whole captured string anyway, so the `tail -3` was
# cosmetic. `echo "$out" | grep -q PAT`, nothing between.
#
# ── Asserting an ABSENCE: prove the search could have succeeded (T-3144) ──
#
# `! grep -q "PATTERN" file` exits 0 when the pattern is absent. It ALSO exits 0
# when the file was renamed, deleted, or is empty — so the leg cannot distinguish
# "the bad thing is not there" from "I could not look", and the gate reports green
# over a check that never ran. Pair every absence assertion with something that
# fails if the search could not happen:
#
#     test -f path/to/file && ! grep -q "PATTERN" path/to/file    # existence first
#     grep -q "KNOWN_MARKER" f && ! grep -q "PATTERN" f           # positive companion
#     cmd > /tmp/.out 2>&1 && ! grep -q "PATTERN" /tmp/.out       # &&-joined producer
#
# Count-equals-zero is the same defect wearing a different hat, and it is the one
# that bites hardest over a COMMAND's output rather than a file:
#
#     [ "$(cargo clippy --workspace 2>&1 | grep -c "^error")" = "0" ]   # WRONG
#
# If cargo is missing, or dies before emitting diagnostics, there are no `^error`
# lines, the count is 0, and the leg passes — a build gate that goes green
# precisely when the build could not run. Measured in this corpus, not invented.
# Keep the producer's exit code in the verdict:
#
#     cargo clippy --workspace > /tmp/.out 2>&1 && ! grep -q "^error" /tmp/.out
#
# T-3144 censused 2853 task files: 71 absence assertions, 41 already correct, 30
# not. The convention mostly works — this note is here so the next one is written
# right, because a vacuous leg is invisible until the day the path moves.
#
# TEST RUNNERS need a guard either way (T-2738). `set -e` is suppressed inside the
# `if` condition the gate runs each line in, so in `cmd1; cmd2` only cmd2 is the
# verdict — and the pass marker you grep for survives a partial failure: a suite
# printing "3 failed, 9 passed" satisfies `grep -q "9 passed"`, and generalising
# to `grep -qE "[0-9]+ passed"` matches the same output. Keep the exit code:
#     python3 -m pytest <file> -q > /tmp/.out 2>&1 && grep -q passed /tmp/.out
# or add the guard the exit code used to supply:
#     out=$(python3 -m pytest <file> -q 2>&1); echo "$out" | grep -q passed && ! echo "$out" | grep -q failed
#     out=$(bats <file> 2>&1); echo "$out" | grep -q '^ok 1 ' && ! echo "$out" | grep -q '^not ok'
# The close gate refuses the unguarded form. Bypass: FW_ALLOW_UNJUDGED_TEST_RUN=1.
#

# shell has no `set -eo pipefail`. A line has returned 0 by hand and 141 under
