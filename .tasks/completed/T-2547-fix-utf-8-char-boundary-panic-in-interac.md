# T-2547: Fix UTF-8 char-boundary panic in interact scrollback diff

## Context

`cmd_interact` (crates/termlink-cli/src/commands/pty.rs) captures a pre-injection
scrollback snapshot's **byte length** (`pre_len = pre_output.len()`, line 66),
then on each poll slices a *later* snapshot at that raw byte offset
(`&full_output[pre_len..]`, line 123). If a multi-byte UTF-8 char (emoji,
box-drawing chars — routine in TUI output) straddles that offset in the later
snapshot, Rust panics: "byte index N is not a char boundary". Discovered by the
T-2468 charter-verb-completeness adversarial review (control-terminal-sessions
lens). The fix walks the split point back to the nearest char boundary; the
per-invocation-unique marker (`pid:nanos`) makes any minor over-inclusion of
prior bytes harmless to marker/exit-code extraction.

## RCA

**Symptom:** `termlink interact <session> '<cmd>'` panics with "byte index N is
not a char boundary" when the PTY scrollback between the pre-injection snapshot
and a poll snapshot contains a multi-byte UTF-8 char straddling the pre-snapshot
byte length (common with emoji or box-drawing TUI output).

**Root cause:** `pre_len` is a byte offset derived from one snapshot
(`pre_output.len()`) but used to slice a *different, later* snapshot
(`&full_output[pre_len..]`). `str` indexing requires char boundaries; a raw byte
offset from a different string carries no such guarantee.

**Why structurally allowed:** the diff was written as a byte-offset optimization
("only search content added since injection") without accounting for UTF-8; PTY
output is arbitrary bytes rendered lossily, so most test/dev traffic was ASCII
and never hit the boundary. No test exercised multibyte scrollback.

**Prevention:** a unit test that slices at a mid-multibyte offset (load-bearing —
panics against the pre-fix code); the char-boundary walk makes any future
byte-offset diff in this path panic-proof by construction.
