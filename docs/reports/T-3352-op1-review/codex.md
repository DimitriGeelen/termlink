### 1. Recommendation: B, with tighter gates

**1a.** Choose **modified B**: inventory in PH-0; A0 immediately after the PH-3 account-creation route exists; the measured-price decision before broader migration; A3 **before configurable PH-4 authority becomes operational**, rather than merely before PH-4 exits. PH-4 development can proceed alongside migration.
**1b.** Pull forward the security-critical portion of A4: any agentic orchestrator, or root process that executes agent-writable scripts, must lose that privilege before declaring A3 complete. Routine operational cleanup can remain in PH-6. A root orchestrator handling agent-controlled inputs is an active escalation path; describing host root as a permanent residual does not make that path harmless.
**1c.** A imposes the entire migration before operational learning. C extends routine root exposure while adding capability. D risks turning a committed target into an indefinite follow-up. B best balances learning and delivery, provided its deadline is enforceable.
**1d.** The post-A0 gate should decide the implementation, budget and schedule—not reopen whether isolation is wanted. If the measured price is unacceptable, hold authority-dependent deployment while revising the migration.
### 2. Practical risk and base-strength releases
**2a.** A prompt injection that induces shell execution already executes with root privileges; no privilege-escalation exploit is required. It can steal sibling credentials, impersonate agents, alter stores and policy, replace launch scripts, or establish persistence. A merely buggy agent can damage unrelated workloads through an incorrect cleanup or ownership command.
**2b.** A compromised remote peer need not defeat TLS or message signatures. It can send authenticated malicious instructions that persuade a receiving agent to execute commands. Section 3.7’s protection against remote attackers therefore needs that qualification: protocol authenticity does not make message content safe.
**2c.** PH-2 at base strength is defensible as a bounded home-lab release if the operator accepts possible loss of the host and its reachable credentials, maintains recoverable backups, and limits access to more valuable systems. PH-3 is harder to justify because fleet admission enlarges exposure. Keep it restricted to explicitly trusted peers until migration completes, with a dated RA-1 review and a deployment gate.
**2d.** Checksums, chains and local logs help diagnose failures; root can rewrite both evidence and its checker. They are not dependable detection against an attacker controlling the host. Account separation materially reduces direct access, but shared executable source remains a lateral-compromise route.
### 3. Price estimates and stage boundaries
**3a.** The S/M/L estimates in section 10.1 are plausible planning placeholders, not a dependable total. Several weeks of work is credible; elapsed time could be substantially longer. **Waves and rollback at S is the least convincing estimate**, given credentials, state ownership, session continuity and partial failures.
**3b.** Likely underestimates are harness authentication and refresh under separate homes; unattended restart; operator attach/inject permissions; and permission drift from editors, builds and Git. A common group fixes many writes but preserves shared-index contention and cross-agent modification of code. Copying one broad credential into every account also preserves a common external compromise domain.
**3c.** A0 should exercise login, credential refresh, attach, restart, commit, tests, messaging and rollback. One successful task cycle and a count of permission fixes cannot price those lifecycle costs. Measure operator time and repeated failures; use a second representative harness or workflow if the estate varies materially.
**3d.** There is a bootstrap gap: A0 requires orchestrator-created accounts through the narrow helper, but A1 nominally builds that helper. Put a minimal compliant template/helper and approval path in A0; A1 generalizes and hardens it. Do not quietly substitute manual account creation.
### 4. Migration failure modes
**4a. Helper.** Fixed settings must constrain names, UID/GID allocation, groups, home paths and templates. Reject arbitrary commands, caller-selected executables and agent-writable hooks. Bind each human approval to one exact creation, with replay protection and defined recovery after partial failure. A single sudoers entry can still expose general root if its target accepts powerful arguments.
**4b. Installed code.** Root-owned binaries are insufficient if agents can redirect hook configuration, modify parent directories, or influence privileged imports and startup scripts. Resolve the documented hook-pinning uncertainty before claiming isolation.
**4c. Mixed estate.** Remaining root agents can access migrated agents’ secrets. Publish migration status per agent and retain the weaker host-wide claim until the last relevant root workload is removed. Test effective identities, supplementary groups and privileged sockets—not just process-name matches.
**4d. Rollback.** “One command” should stop and fence the current instance before restarting its predecessor, preserve state ownership and prevent duplicate identities. Returning to root is an explicit security downgrade requiring the applicable approval and visible status. After suspected compromise, rollback alone is insufficient: rotate exposed credentials and restore trusted code.
### 5. One-line verdict
**Modified B: measure early, then require effective isolation before operational configurable authority—the strongest reason is that agent-unwritable policy cannot exist while those agents retain root or a writable route back to it.**
