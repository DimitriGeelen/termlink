# GLM (opencode, zai-coding-plan/glm-5.3) on FX-5 and the artifact store — 2026-10-13

1. **Option C, amended.** Counting alone (A) makes the baseline "honest" while blessing the attachments build to pour a new content class through a plaintext store the metric cannot see — a guard whose green survives the exact harm the floor names is worse than no guard. B and D leave the baseline understated: the store exists at PH-0, so a floor measured against a partial inventory isn't a floor. Amend C in one way: scope the check to **every writer of the artifact-store API** (CLI verbs, MCP tools, future rails), not "sidecar code" — a sidecar-only rule is one new call site away from silent bypass.
2. **Yes, it is growth.** FX-5's sentence governs *readable content in a form readers can read*; the field count is the check, not the floor, and substituting a proxy for the floor is the error to avoid. "What today's rails already expose" means today's *exposure*, not today's *plumbing* — otherwise the floor is vacuous, since every future feature is a new use of existing RPCs and disk. What grows: a new content class (agent conversation attachments), new volume (2 GiB blobs, effectively unbounded in aggregate), and defaultness without consent — users choose `file send`; they don't choose that every attachment their agent sends lands plaintext on hub disk.
3. **Fields is the wrong metric; it measures surface shape, not disclosure.** It stays flat when readers widen, flat when a new content class rides an old field, and it is blind to volume and to per-message encryption status. Better: an inventory of (content store × form: plaintext/ciphertext × reader class: operator/token tiers), checked as "no new row, no row downgrades to plaintext, no reader set widens" — mechanically diffable, same idiom as this repo's allowlist checks. Volume (the 2 GiB ceiling) deserves its own bound, as does per-field size (see 4).
4. **Partially enforceable; static-only is not enough.** A grep/AST check can enumerate artifact-store write call sites and fail any not passing through the encrypt wrapper — the established sink-check pattern. It cannot see plaintext-ness (a disabled or mock cipher passes), so make the hub the enforcement point: refuse artifact writes lacking a recipient-encryption envelope, turning a source convention into a runtime invariant. It also misses tunneling — base64 a file into an already-counted field leaves the count flat while the file sits on disk; a per-plaintext-field size cap catches this — and it misses non-sidecar writers (fixed by 1). Encrypt-to-recipient is right even with operator==host: the same-person argument proves too much (it would equally justify leaving later-phase turns plaintext, which the arc rejects); top-tier *token holders* are not the operator; and encrypting turns while their attachments — often the sensitive payload — sit plaintext makes the turn encryption theater.
5. **Framing.** Recommending against the top score is correct: floors are constraints, not objectives, and a driver set (antifragility, reliability, usability, count-truthfulness, operator-simplicity) structurally cannot price confidentiality — so A's +22 is not evidence against C; the scoring was the wrong instrument for this clause and should be recorded as inapplicable, not as a near-loss C survived. Real biases/gaps: (a) the author-intent question ("did FX-5 mean the store?") should be settled by the author or recorded as a decision, not adjudicated inside a consult — otherwise the next measurer re-litigates it; (b) C's check is presented as general when it patches one known blind spot of a weak proxy — state that scope on the check's own output; (c) nobody noted that recipient-encryption machinery arrives in later phases anyway, so building attachments on the plaintext store now purchases a future migration — an antifragility argument for C the drivers missed. C's usability costs (key distribution, losing SHA-256 dedup, no operator recovery) are real but are consequences of the floor, not grounds to waive it.
