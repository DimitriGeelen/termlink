# Codex (gpt-6-astra, read-only) on FX-5 and the artifact store — 2026-10-13

1. **Pick C, with a stronger, explicitly bounded rule.** The artifact store belongs in the disclosure baseline: it stores content readable by both the hub operator and an authorized token holder. Excluding it because it is outside the message rails contradicts the floor’s broader wording. Record it as a ninth counted surface, while acknowledging that a blob store is not directly comparable to a message field. Freeze the PH-0 inventory and reader permissions; adding this omitted surface corrects the measurement, not authorizes new disclosure. For attachments, prohibit new hub-readable copies through *any* route, rather than only sidecar writes to this store.

2. **Attachments plausibly constitute growth, but the text does not settle that conclusively.** There are two reasonable interpretations:
   - **Capability baseline:** Today’s file rail already exposes arbitrary files to these readers, so another interface using that rail adds no disclosure capability.
   - **Workflow baseline:** Automatically depositing agent attachments creates readable copies that the previous agent-message workflow did not create, expanding disclosure.

   The proposer assumes the second interpretation. I favor it because otherwise an existing arbitrary-file store effectively exempts every future content type, making “No feature writes content … beyond” nearly toothless. Nevertheless, attachment contents are not necessarily a new content class, and a new interface alone does not prove new exposure. The operator should explicitly adopt the workflow interpretation, distinguishing a genuinely new copy or reader from reuse of an already-disclosed artifact.

3. **Field count is a useful tripwire, not an adequate confidentiality metric.** One field can hold a conversation, an archive, or 2 GiB of files; adding sensitive payloads to it changes no count. Use a disclosure inventory whose entries identify content class and source workflow, storage location, readable principals, encryption/key access, retention, and replication. Review each feature for newly exposed combinations of these attributes. Track volume separately—especially retention and accumulated readable bytes—but do not demand zero byte growth from normal use of existing rails unless that is truly intended. A defensible floor is “no new exposure relationships or broader retention,” with field count as a supplementary check.

4. **C’s static check is enforceable only as a limited architectural guardrail.** A dependency or call-site rule can forbid direct sidecar access to plaintext artifact-upload APIs. It cannot reliably establish that arbitrary bytes are encrypted correctly or catch every indirect path. It may miss helper services, alternate storage, logs, previews, temporary files, weak encryption, exposed keys, and permissive downloads. Centralize attachment handling, require a defined encrypted envelope, and test authorization, storage, and failure paths. “Encrypt to the recipient” should mean the intended authorized reader set, with keys unavailable to hub credentials. Because the hub and host operator are the same person, encryption protects stored hub data and token access but cannot promise secrecy against an operator able to inspect sidecar memory or keys. State that threat-model boundary explicitly.

5. **Rejecting the highest score is justified only after establishing floor compliance.** A weighted score cannot compensate for violating a mandatory constraint; confidentiality need not be another weighted driver. But A’s disqualification depends on the disputed interpretation, not merely on asserting “floor.” The framing also overstates what C’s narrow check guarantees and mixes baseline truthfulness with future-feature permission. Decide those separately: count the store now, clarify what constitutes new disclosure, then compare compliant implementations on the weighted drivers.
